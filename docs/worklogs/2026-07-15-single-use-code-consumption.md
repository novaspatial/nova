Single-use code consumption

Date: 2026-07-15.

Codes now consume (#26, D6): `discount_codes` grew `reserved_count`/`redeemed_count`, checkout acquires an atomic hold per catalog code (`reserve_discount_code`, a first-mix-style CAS re-checking active/expiry and capacity `single_use ? 1 : usage_limit`), `release()` and the DELETE route return it, and confirmed payment finalizes it — the webhook calls `consume_discount_code`, idempotent per project via the new `discount_redemptions` ledger PK, moving 1 unit from held to redeemed. A failed consume 500s the webhook and the idempotent replay path re-attempts it, so a claim-landed-consume-failed retry can never strand a code; the payment-status poll and the dev-bypass insert finalize best-effort. The 3 RPCs are EXECUTE-granted to service_role only (in-body guards survive ACL drift): with no per-user identity to guard on, an authenticated grant would let any signed-in user burn capacity through raw PostgREST — so checkout resolves the service client for catalog-code orders, while WELCOME and no-code checkouts still never touch it.

The concurrent-WELCOME D5 race (#25's second residual) closes at the DB floor: a partial unique index allows 1 WELCOME row — pending or paid — per owner, the losing insert's 23505 maps to a 400 (`welcome_in_use`), and deleting the abandoned row frees the slot. Restore-on-abandon moved out of `cleanupProjectArtifacts` (now storage-only) into the DELETE route, keyed on the delete-returning row so 2 concurrent deletes can't double-decrement a hold; the accepted trade is that a crash between delete and restore leaks 1 hold, recoverable with `update discount_codes c set reserved_count = (select count(*) from projects p where p.applied_coupon_code = c.code and p.paid_at is null);`.

D-floor-private shipped in the same slice: `allow_below_floor` (private-only by CHECK, set at creation — the admin PATCH stays active-toggle-only) rides the widened `lookup_discount_code` into the OrderCode, and `computeOrderPrice` drops the floor to 0 for flagged codes (the 35% cap still binds percent codes at $211.25/song). Checkout rejects totals under Stripe's 50-cent minimum with a 400 and releases the hold — no clamp, no free-order path. The resolver also pre-checks capacity (`exhausted`, "no longer available"), which the validate endpoint inherits, and the admin list shows `redeemed R/limit` plus a below-floor marker.

Applied to the remote (`20260715_consume_discount_codes`; pre-flight found no per-owner WELCOME duplicates, grant probes and advisors clean) and verified by the 758-test suite, lint, and build. Residuals: abandoned-but-undeleted `pending_payment` rows hold capacity until deleted (no sweep — candidate rider for #27); a #43 direct insert can stamp an `applied_coupon_code` without a hold, so a later #42-style payment would burn that code's capacity (griefing-only — the DB floor belongs to #42/#43); #24 lands next in the webhook, whose post-claim order is documented in the handler: consumption (must-500) before the email (best-effort).
